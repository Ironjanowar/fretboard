## Confirmed product contract

- Add `Piano` to the existing instrument selector; retain stable current instrument identifiers.
- Display a fixed keyboard from C3 through B5. No octave/range selector.
- Visualizer: show every occurrence of each active chord note within that range, not a proposed voicing or hand position.
- Preserve white and black keys; overlay note markers using the existing chord palette. Preserve chord highlight and removal behavior. Shared notes must remain intelligible when multiple chords are active; prefer existing overlap semantics rather than introduce another display mode.
- Visible note labels appear ONLY on active notes: chord notes in the visualizer, selected keys in the analyzer. No permanent C3/C4/C5 labels. Accessible names may identify all keys without adding visible labels.
- Analyzer: clicking/tapping a key toggles that exact pitch independently. Repeated pitch classes at different octaves remain separately selectable. No string-style one-note-per-string rule or artificial finger-count limit.
- Reuse existing empty, single-note, interval, octave, chord, bass and inversion result semantics.
- No piano tuning button, tuning modal or emitted tuning URL parameters. Reject/ignore irrelevant tuning events for piano rather than only hiding the button.
- Switching between piano and any string instrument clears analyzer selection, including when the visualizer tab is active. Preserve the active chord list. Do not introduce per-instrument selection memory or convert positions into pitches across that boundary.
- Keep current behavior when switching between string instruments, including tuning reset and marked-position filtering. Preserve existing highlight-reset behavior on instrument changes unless tests reveal an agreed contradiction.
- Switching tabs within piano retains selection. Reloading or sharing the URL restores the selected keys, instrument, tab, chords and highlight.
- Mobile: horizontally scroll the keyboard at usable key sizes; avoid shrinking it into tiny hit targets or causing page-wide horizontal overflow.
- Keep the existing cards, controls, suggestions and overall page structure. Keep all application and repository documentation copy in English.

## Non-goals

Audio, MIDI, pedals, velocity, fingering, hand allocation, voicing generation, configurable piano tuning, range controls, a general instrument plugin framework, a full LiveView rewrite, a redesign of the website, new chord recognition rules, and replacing all existing instrument URLs.

## Findings from current code

- `lib/fretboard/music/instrument.ex` assumes all catalog entries have strings, frets and pitch presets. Simply adding `:piano` to the instrument list will break callers that unconditionally ask for string/tuning data.
- `lib/fretboard/music/analyzer.ex` converts `{string => fret}` to absolute pitches and then performs instrument-independent analysis. Extract that pitch-based core; retain the existing adapter and public API for regression compatibility.
- `lib/fretboard/music.ex` is the sole music facade available to the web layer. Its chord lookup can support keyboard note membership without duplicating chord formulas.
- `lib/fretboard/music/url_codec.ex` currently decodes a tuning state for every instrument. Its `pitches` parameter already means open-string tuning pitches; do NOT reuse that parameter for selected piano keys.
- `lib/fretboard_web/live/fretboard_live.ex` decodes tuning, string count, fretboard data and analysis unconditionally. `change_instrument` also assumes a Standard tuning. URL-building helpers always encode tuning and a string-position selection.
- `lib/fretboard_web/components/fretboard_svg.ex` contains the current instrument rendering and overlap/highlight conventions. Keep it working for strings rather than forcing piano through fret geometry.
- `priv/static/assets/css/app.css` is the discovered non-digested stylesheet. Confirm it is the tracked source before editing; do not edit fingerprinted generated CSS.

## Proposed technical contract

### Instrument metadata and selection

Add a minimal instrument distinction (e.g. `kind: :fretted | :keyboard`) in catalog metadata, exposed through `Fretboard.Music`. Piano metadata describes a fixed pitch range and no tuning capability; it has no fabricated string count or pitch presets. Keep existing string APIs and their behavior intact for current callers.

Use the known instrument and its capability to choose rendering, URL decoding and event handling. Do not scatter checks throughout unrelated chord/domain functions or introduce redundant state flags.

Retain string-position selection for fretted instruments. Represent piano selection as a set/list of unique absolute pitches, independently of chord pitch-class membership. Choose the smallest explicit LiveView state shape that supports both; do not maintain a second hidden per-instrument history. Any new state contract stays derived in `handle_params`.

### Domain interface

Proposed new facade functions (names may be refined with tests):
- `Music.analyze_pitches(pitches)` delegates to the extracted analyzer core.
- `Music.keyboard_data(pitches, active_chords)` produces musical key data (absolute pitch, note name, chord membership), not SVG coordinates or CSS colors.
- `Music.decode_page_params(params)` and `Music.encode_page_params(state)` provide the instrument-aware page contract: `%{instrument: ..., tuning_state: ..., active_chords: ..., highlighted_chord: ..., tab: ..., selection: ...}`. Piano has `tuning_state: nil` and a list of unique selected absolute pitches; fretted instruments retain tuning maps and marked-position maps. Preserve existing string-oriented facade entry points and return shapes. During phase 1, the legacy decoder remains fretted-only (including safe guitar fallback for `instrument=piano`) and the current UI uses a fretted-only list; phase 2 switches the LiveView to the new page contract.

Existing `Music.analyzer_state(marked_notes, string_pitches)` should derive pitches and call the same core. Sort before determining bass and deduplicating pitch classes. Preserve duplicate-octave behavior and existing recognition rules.

Keep keyboard layout geometry in the web component, not in music modules. Only the facade may be called by the web layer.

### URL boundary

- Use `instrument=piano` and a distinct `keys` parameter for selected absolute pitches, serialized in ascending order without duplicates.
- Retain `tab`, `chords` and `highlight` meanings. Omit `keys` for an empty selection.
- For piano, ignore legacy `marked`, `tuning`, `pitches` and `reference`; do not emit them in newly generated piano URLs.
- For string instruments, ignore `keys`; preserve existing `marked` and tuning behavior.
- Validate piano key tokens as complete integer strings inside the fixed range. Ignore invalid entries, deduplicate valid ones, and treat a non-string keys value as empty without losing valid sibling fields.
- Do not create atoms from arbitrary input. Guard direct events as well as URL input.
- URL reload and back/forward navigation must recompute from URL, not leak a cached result from the other instrument or tab.

## Risk and complexity assessment

Overall: medium implementation complexity, localized visual impact.

- Low risk: chord formulas, scale/progression logic, existing result cards and palette reuse.
- Moderate risk: keyboard geometry, marker readability and mobile touch behavior.
- Highest risk: removing unconditional tuning assumptions, adapting URL-backed selection and avoiding stale derived analysis. Regression tests are essential.
- Avoidable scope growth: converting selections across instruments, full piano range navigation, voicing suggestions, and a generic instrument framework are explicitly excluded.
